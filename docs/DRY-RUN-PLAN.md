# Bounded manual dry run

Status: local preparation only. No workflow has been pushed or run. The dry run uses the checked-in sanitized Taipei fixture and the pinned geometry, with no R2, source HTTP, or secret access. It constructs a complete manifest and 32 shards and prints a bootstrap would-be plan; it does not inspect a bucket, so this is not a prediction of changed shards or a storage safety check against existing objects.

Preconditions: public repository on its default branch contains reviewed source and workflow, Actions is permitted, `LIVE_STATUS_PUBLIC_REPOSITORY` is set exactly to `woodstockv/taipei-parking-live`, the job passes its public-repository and default-branch guards, and `LIVE_SCHEDULE_ENABLED` is unset or not `true`. GitHub Actions must be available and eligible for the public runner. No R2 configuration is needed for this dry run. Verify provenance, geometry, dependencies, tests, reader budget, and this workflow before release; the unresolved geometry source record remains a release gate.

Dispatch **Live parking status** on the default branch with `dry_run=true` (the default). Expected JSON: `mode=fixture-dry-run`, 51,536 geometry rows, `computedManifests=1`, `computedShards=32`, 32 hypothetical shard PUTs plus one manifest PUT, and actual A=0, B=0, PUT=0, DELETE=0. It checks the gzip hash and partition membership before producing the plan. Node may print an experimental transform-types warning. There are no LIST/GET calls. Estimated empty-bucket real bootstrap: 36 Class A (32 shard PUTs, retention-index PUT, manifest PUT, ledger PUT, one LIST) and 4 Class B GETs (ledger, checkpoint, current manifest, retention index), excluding failures. Its ledger reserves conservatively; attempted operations may differ. A warm full-change run with one inventory page is 37 A and 4 B, unchanged/304 5 A and 4 B; excludes GC, retries, failures and reader traffic.

Abort if job is skipped unexpectedly, source/hash/partition validation fails, counts differ, any network or storage write appears, logs expose credentials, a concurrency guard is bypassed, or usage/headroom and geometry provenance are unresolved. Disable further runs and investigate. Dry-run credentials are not passed to the step.

Only after explicit Forge/Viv go, a separate single `workflow_dispatch` with `dry_run=false` may publish once, with the schedule still disabled. This uses the live public source and R2 and writes objects. Beforehand, require a dedicated bucket, reviewed account-wide usage/billing and reader budget, sole writer, R2 variables and secrets, storage/inventory headroom, operational owner, and verified CORS/cache serving path. Review source status, accounting, manifest, shards, hashes and metadata after; stop on failure. The wrapper does not run GC. Sustained schedule remains blocked until a separately reviewed retention/GC plan is implemented: the 10,000-object cap can be reached before the 48-hour grace period at high churn. No approval to publish or activate is implied here.

For planning at 12 runs/hour, one inventory page, no GC or failures: 30 days (8,640 runs) at 37 A / 4 B each is **319,680 A / 34,560 B**; 31 days (8,928 runs) is **330,336 A / 35,712 B**. At unchanged/304, 5 A / 4 B gives 43,200 A / 34,560 B and 44,640 A / 35,712 B respectively. These are actual-request scenarios, not a guaranteed limit; retention, extra inventory pages, failed requests, account-wide activity and readers change totals. Upstream's conservative 30-day reservation bound for full-shard cycles with ten inventory pages is 397,440 A; adding 360 hypothetical 96-A GC reservations produces 432,000 A, but this wrapper does not run GC.
